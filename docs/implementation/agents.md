# Codex specialist agents

SchemaForge defines six project-scoped Codex specialists in `.codex/agents/*.toml`. The definitions use Codex's native TOML agent-file format: `name`, `description`, and `developer_instructions` are required; optional settings are limited to supported Codex config keys. No role pins a model, provider, or reasoning effort, so those resolve through the spawning request and parent configuration.

`.codex/config.toml` enables the agent tools and sets `max_concurrent_threads_per_session = 3`. That field counts spawned agent threads and excludes the primary thread, for at most four total threads in one Codex session when the setting is honored. In this repository context, Codex CLI 0.161.0 reports `multi_agent` as stable and enabled; `multi_agent_v2` is stable but disabled. The official custom-agent configuration documentation does not state that `multi_agent_v2` must be enabled, so the project does not turn it on speculatively. Runtime discovery of these role files has not been tested. The current execution harness can impose a stricter concurrency limit; a config value cannot create extra harness capacity.

The `security` and `qa` agents set `sandbox_mode = "read-only"`, which asks Codex to run their shell work under its read-only sandbox. The other roles inherit the parent sandbox and approval context. `sandbox_mode` does not set an approval policy. There is no dangerous bypass or approval-policy escalation in these files. Project instructions about exclusive paths, no Oracle access, no external writes, and bounded work are task constraints; they are not independent operating-system access controls. In particular, unrestricted shared-harness tools can exceed a role's written boundary unless the harness itself enforces it.

The six role prompts define the requested continuing ownership domains: database/Oracle runtime; backend contracts, metadata and worker; frontend workflows over stable contracts; security and license compliance; QA and acceptance evidence; and DevOps/reproducible operations. For this session, the repository's `AGENTS.md` limits actual work to Phase 0/offline WP0. The role files preserve that current guard while allowing future work in each domain only after the orchestrator authorizes the phase and assigns a bounded task. Oracle behavior remains unverified until the required lab evidence exists. Security and QA default to read-only reviews. The orchestrator always controls phase, authority, shared files, tracking, and integration.

If a later execution environment lacks native subagent dispatch or does not load these project roles, do not claim delegation occurred. The orchestrator should issue bounded assignments sequentially using the available tools and preserve the same exclusive-file ownership and review requirements.

## Runtime boundary

The project role registry is a Codex CLI configuration feature. It is not automatically consumed by every orchestration harness. In the current harness, delegated tasks arrive through explicit `spawn_agent` task instructions, with follow-up and coordination through `followup_task`, `send_message`, `list_agents`, `interrupt_agent`, and `wait_agent`. That dispatch surface does not itself load `.codex/agents/*.toml`; the orchestrator must explicitly supply each assignment and review the result. Therefore these role files document and configure native Codex CLI specialists where that registry is active; they do not claim that the current harness used those role definitions.

Codex CLI specialist files and multi-agent settings are documented at [Subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents) and [Configuration reference](https://learn.chatgpt.com/docs/config-file/config-reference). The CLI and feature-flag observations for this setup are recorded in [runtime-validation.json](runtime-validation.json). Local verification deliberately avoids starting a model turn or making an Oracle/external connection.
