Upstream lifecycle (S B03): ACTIVE → DELETED is soft archive; DELETED → ACTIVE is restore; permanent purge requires prior archive and rejects the built-in default project. Archive preserves databases/issues. API state and permission checks are authoritative even when an action is visible.

Do not transplant workspace inherited authority. The implementation contract is in [Phase 1 specification](KELYRVO_PHASE1_SPECIFICATION.md).

Release check may use live targets; it is not equivalent to Kelryvo offline parser validation. | S B01, B08 `release_service.proto:20–109` |

Upstream review lifecycle (S B08–09 and `proto/v1/v1/common.proto:102–129`): linked Issue starts `draft=true`; submission removes draft and initiates approval finding (CHECKING then PENDING/APPROVED/REJECTED/SKIPPED as applicable). Approval status is separate from Issue OPEN/DONE/CANCELED and Plan ACTIVE/DELETED. Approve/Reject POST `…/issues/{I}:approve` / `:reject` use custom approval-flow authority, not a blanket permission bit. Approved/current checks can generate rollout; run moves tasks through pending/running to terminal result, with separate attempt records. Do not flatten those independent states into a single “deployed” flag.

Important divergences: Bytebase Plans can be edited and checks rerun; Kelryvo retained plans are immutable. Bytebase rules can require no human approval and supported API/GitOps paths can be issueless. The pinned rollout proto explicitly documents live database-group expansion after approval. Kelryvo always requires independent approval and freezes exactly one resolved target per initial plan; no live group expansion, automatic rollout, retry/skip or implicit environment promotion is adopted. These are deliberate **I** safety adaptations, not claims of upstream parity.
